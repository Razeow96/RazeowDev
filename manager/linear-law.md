# Linear law

`LIN LAW v1 LOADED`

The one home for how every seat reads and writes Linear. Act-scoped law (structure-law §2): loaded by any skill or step that touches Linear — /start, /startceo, /status, /dump, /routetask, /weekreview(ceo), close sweeps, Laura's Linear surface. Skills cite LIN IDs and never restate them. Consolidated 2026-08-30 from learnrule #38 + six skills (an internal ticket).

## Reading

- **LIN-1 · Pull by team + cycle, never filter the query by project.** Sprint sessions are routed to their destination projects, so a project-filtered pull silently hides them. Scope is applied client-side after the pull (LIN-11).
- **LIN-2 · The sprint number IS the Linear cycle number — one number, one name.** "Sprint 8" and "cycle 8" are the same week; the number always comes from the live pull, never from memory, and no surface (session.md, plan docs, ticket text, chat) may carry a spoken sprint number that differs from Linear's. Headers print `Sprint N (cycle N from Linear)`.
- **LIN-3 · Carry-over compresses.** An issue in the active cycle whose `createdAt` predates the cycle's start is carry-over — one count line (`CARRY-OVER: N open`), never table rows.
- **LIN-4 · Done rows age out at 3 days** in sprint tables — older Done collapses to one count line. UNPROVEN and BLOCKED are never age-filtered.
- **LIN-8 · Linear beats `session.md`.** session.md is rewritten only at close, so mid-session it is stale; on any disagreement Linear wins and the drift is noted in one line.
- **LIN-9 · Mechanics:** `list_cycles` needs the team UUID; the big backlog pull has no cycle field — pull sprint issues by cycle id.
- **LIN-10 · "Today" = Raze's local day (UTC+8)**, derived from Linear timestamps (`completedAt`/`updatedAt`), never from chat memory.
- **LIN-11 · Scope by seat:** HQ surfaces (CEO skills, Laura) read org-wide; a subsidiary repo's surfaces keep only that repo's project rows.
- **LIN-12 · The five reads** (ages always printed): Backlog routed (waiting N days) · reroute queue = Backlog with no project · In Progress (since startedAt) · In Review (pending N days) · Done. Todo is kept as a state but is NOT a read surface — cycle membership answers "planned".

## Writing

- **LIN-5 · Born with its cycle, under its session.** This week's work → the active cycle; filed at Sunday planning → the `next` cycle. A task is created as a sub-issue of its session parent (LIN-14) with its three labels (LIN-13) at creation. Due dates only for real external deadlines.
- **LIN-6 · Carry-over moves** to the next cycle at planning — never duplicated.
- **LIN-7 · Verdict → state map (routing):** move to the destination project, never duplicate · do-now = Todo + active cycle · hold = Backlog + `hold` label · drop = Canceled, **only on Raze's explicit call, never deleted** · Done = closed: a `general` task on the owner's word (a Telegram Done tap counts), never a `software` or `marketing` task · In Review = marked done by the owner, evidence not yet checked (LIN-15) · Verified = review passed, evidence linked (LIN-15) · In Progress = started · Duplicate marks the surviving issue. States reconcile at every session close.
- **LIN-13 · Labels — four groups, every task carries its set.** `sess` group = issue type (`build` / `plan` / `maint` / `learn`), one per task. `Work` group = how the task closes (`software` / `marketing` / `general`), exactly one per task — software and marketing pass the review gate, general closes on Done (LIN-15). `obj` group = the objectives' **full names as maintained in the Brain** plus `side quest`; exactly one per task — `side quest` is work that serves no objective on purpose (learning, chores, favours) and is an explicit call, never a default. `kr` group = key results' **full titles**, but ONLY those with a `kr_sprint_targets` row in the current cycle; the group is regenerated every Sunday at planning (add the newly targeted, retire the rest) so it never grows past the sprint's focus. An objective-tagged task carries exactly one `kr` label; a `side quest` task carries none. **Drift, mechanically:** an objective-tagged task with no `kr` label, a task with no `obj` label at all, or a task with no `Work` label. Session parents (LIN-14) carry no labels — labels live on tasks. Brain-dump capture is verbatim and **unlabelled** — labelling happens at /routetask or at planning, sessions Raze calls, never on a schedule.
- **LIN-14 · Session model — parent per session, tasks as sub-issues.** A sprint week is 7 days × three session kinds: **S1 = 4 hours · S2 = 2 hours · S-B = session bonus**, variable length, minted only on the morning the free time exists (an 8am start = one S-B before S1), never pre-planned. Each session is a **parent issue** in project Executive, active cycle, titled `<Day> <S1|S2|S-B> — YYYY-MM-DD`, description = the **timetable**: ordered blocks with durations (standing items first — e.g. the 20-minute ads check — then the tasks, then a closing proof-and-tickets block). A block that belongs to a task carries that ticket right after its number — `1. [an internal ticket] Client batch 3 · 60 min` — so the CEO bot (HQ-M0.9) can show each task with its block numbers and total minutes; a block with no ticket (ads check, proof and tickets, reserve) renders as one No ticket line. Every task is a **sub-issue** of its session parent, in its own destination project, with its own type · work · objective · key-result labels and its own Done line. A task with no parent is unslotted and lives in Backlog, never Todo. Parent state rolls up: In Progress when the session opens, Done when every child is Done or explicitly moved to another parent; a parent never carries work of its own. Sprint tables render **grouped by parent** — the parent row, then its children indented — so a session with no children, or a child with no parent, is visible as a finding.
- **LIN-15 · Review gate — who checks, and how.** Marking a `software` or `marketing` task done (a CEO bot Done tap, HQ-M0.9, or a session call) moves it to **In Review**, never Done; a `general` task goes straight to Done. The In Review queue is cleared at **every close session** (/close, /closeceo step 5) by the operator seat — never by an agent (MGR-23). Evidence by label: `software` = the real run observed (the qa-verifier agent may gather the payload evidence; the operator reads it before acting, LEAD-22) · `marketing` = a live link, screenshot or metric number, from the owner's reply or checked live by the operator. Pass → **Verified** with the evidence as a comment. Fail → In Progress with the gap named. No evidence and the owner absent → stays In Review, printed with its age (LIN-12), never promoted on silence. A task with no `Work` label is drift: the bot asks which kind before it moves anything. Verified is a completed-type workflow state added by the owner in team settings.
