# Linear law

Type: Law · how every seat reads and writes Linear; pulled through rulesindex by any skill or step that touches Linear — /start, /startceo, /status, /dump, /routetask, /weekreview(ceo), close sweeps, Laura's Linear surface. Update: one rule = one line; replace the line and delete the superseded one in the same edit. The reasoning and the incident behind each rule: `rsot/knowledge/linear-law-rationale.md`, same rule IDs, open when a rule's judgment is in play.

## Reading

- **LIN-1 · Pull by team + cycle, never filter the query by project;** scope is applied client-side after the pull (LIN-11).
- **LIN-2 · The sprint number IS the Linear cycle number,** always taken from the live pull, never from memory, no surface (session.md, plan docs, ticket text, chat) may carry a spoken sprint number that differs, and headers print `Sprint N (cycle N from Linear)`.
- **LIN-3 · Carry-over compresses:** an open issue in the active cycle whose session parent is dated before the cycle's start, or has no parent in this cycle, renders as one count line (`CARRY-OVER: N open`), never as table rows; date fields are never pulled to decide it.
- **LIN-4 · The boot reads today, the weekly review reads the cycle:** a boot or status read pulls the cycle's open rows only (Todo, In Progress, In Review; Done, Verified and Canceled rows are never pulled unless the owner asks to see them, the cycle header carries the Done count) with fields `id · title · status · labels · parent` and lists today's session parents with their tasks plus yesterday's parents still open as question rows; every other day of the cycle is one count line (`<Day> · N open · N done`); Done rows never list at boot and Backlog is never read at boot (routing reads it); UNPROVEN and BLOCKED are never filtered; `/weekreviewceo` is the one read of the whole cycle (owner ruling 2026-10-15).
- **LIN-8 · Two surfaces, two contents:** Linear holds task state (open · in review · done), `session.md` holds what exists, what is blocked and what is next, neither restates the other, and at /close Linear is updated first, then session.md is written.
- **LIN-9 · Mechanics:** Method: `rsot/knowledge/linear-api-mechanics.md`.
- **LIN-10 · "Today" = Raze's local day (UTC+8),** derived from Linear timestamps (`completedAt`/`updatedAt`), never from chat memory.
- **LIN-11 · Scope by seat:** HQ surfaces (CEO skills, Laura) read org-wide and a subsidiary repo's surfaces keep only that repo's project rows.
- **LIN-12 · The five reads,** ages always printed, are Backlog routed (waiting N days) · reroute queue = Backlog with no project · In Progress (since startedAt) · In Review (pending N days) · Done, and Todo stays a state but is never a read surface.

## Writing

- **LIN-16 · Linear tracks work, never the truth:** it holds only ideas, issues, the sprint and its session parents, and one task per thing done today, while designs, decisions and facts live in the board and the msot/sot docs the issue links.
- **LIN-17 · Large work = one task per chunk,** each chunk closed by Raze's verdict.
- **LIN-18 · Issue first:** the issue (scope, acceptance criteria, links to the board page and the sot doc holding the design) is written or updated before the work and code follows the ticket, as an order rule, never an approval gate.
- **LIN-19 · Proven run = Done:** never Done until the main path ran once for real and the result was observed (on a phone for any UI, end to end for anything spanning two or more domains) with the evidence link in a comment, and until then the status reads "self-tested vs mocks, awaiting live proof."
- **LIN-20 · Go-live prerequisite:** a go-live prerequisite is stated once, in its issue, then dropped, and who deploys, goes live and what waits for approval is the global card §3, narrowed in a repo only by a dated exception in its own rule file (LEAD-26).
- **LIN-5 · Born with its cycle, under its session:** this week's work goes to the active cycle and work filed at Sunday planning to the `next` cycle, each task is created as a sub-issue of its session parent (LIN-14) with its labels (LIN-13) at creation, and due dates are set only for real external deadlines.
- **LIN-6 · Carry-over moves** to the next cycle at planning, never duplicated.
- **LIN-7 · Verdict → state map (routing):** move to the destination project, never duplicate · do-now = Todo + active cycle · hold = Backlog + `hold` label · drop = Canceled, **only on Raze's explicit call, never deleted** · Done = closed (LIN-15) · In Review = marked done by the owner, evidence not yet checked (LIN-15) · Verified = review passed, evidence linked (LIN-15) · In Progress = started · Duplicate marks the surviving issue · states reconcile at every session close.
- **LIN-13 · Labels — four groups, every task carries its set:** exactly one `sess` type (`build` / `plan` / `maint` / `learn`), exactly one `Work` (`software` / `marketing` / `general`; software and marketing pass LIN-15), exactly one `obj` (an objective's **full name as maintained in the Brain**, or `side quest` only as an explicit call, never a default), and on an objective-tagged task exactly one `kr` (a key result's **full title**, only those with a `kr_sprint_targets` row in the current cycle, the group regenerated every Sunday at planning; a `side quest` task carries none), while session parents (LIN-14) and verbatim brain-dump captures stay **unlabelled** until /routetask or planning, never labelled on a schedule, and a task missing its `Work`, `obj` or required `kr` label is drift.
- **LIN-14 · Session model — parent per session, tasks as sub-issues:** a sprint week is 7 days of **S1 = 4 hours · S2 = 2 hours · S-B = variable**, S-B minted only on the morning the free time exists and never pre-planned unless the owner rules a standing S-B (a fixed 2-hour block created with the skeleton at Sunday planning; current: the daily Upwork window, 1 hour at 9–10 PM MYT, from 2026-10-23, ruled 2026-10-19; the Nick Saraev course is on hold), each session is a **parent issue** in project Executive, active cycle, titled `<Day> <S1|S2|S-B> — YYYY-MM-DD`, whose description is the timetable of ordered blocks with durations (standing items first, then tasks with the ticket right after the block number as `1. [an internal ticket] Client batch 3 · 60 min`, then a closing proof-and-tickets block), every task is a **sub-issue** in its own destination project with its own labels and Done line, a task with no parent lives in Backlog, never Todo, the parent goes In Progress when the session opens and Done when every child is Done or explicitly moved, never carrying work of its own, and sprint tables render **grouped by parent**, children indented.
- **LIN-15 · Review gate — who checks, and how:** marking a `software` or `marketing` task done moves it to **In Review**, never Done, and a `general` task goes straight to Done; the operator seat, never an agent, clears In Review at **every close session** (/close, /closeceo step 5) on evidence by label (`software` = the real run observed, and the qa-verifier agent may gather that payload evidence, global card §3; `marketing` = a live link, screenshot or metric number), pass → **Verified** with the evidence as a comment, fail → In Progress with the gap named, no evidence with the owner absent → stays In Review with its age (LIN-12), never promoted on silence, and a task with no `Work` label is asked about before anything moves.
