# Figma law — the boards

Type: Law · how every repo uses Figma: which boards exist, how their pages are ordered, how a board is approved and changed, and where its link lives; pulled through rulesindex whenever a task creates, edits, reads or links a board. The per-kind drawing recipes are the drawing law, `rsot/rules/drawing/`. Update: one rule = one line; replace the line and delete the superseded one in the same edit. The reasoning and the incident behind each rule: `rsot/knowledge/governance-law-rationale.md` §figma-law, same rule IDs, open when a rule's judgment is in play.

- **FIG-1** Figma is the sole visual surface of the org: each project has one Figma folder named `<code> · <name>` holding two FigJam boards, the state board `<code> · <name>` (system design · flow · schema, the approved state and the truth, DRAW-29) and the workspace board `<code> · <name> · Workspace` (discussion sketches and options, Draft like `/workspace`, never cited as truth; an approved drawing is redrawn on the state board, never moved there); a new project gets both boards when its first drawing starts; proposal assets for prospects follow their company's card, not this file (owner ruling 2026-10-21).
- **FIG-2** Pages run domain, then module: page 1 is the domain high level, then one page per module inside that domain, and the drawing kinds (flow, schema, context map, UX) are sections on the module's page, never pages of their own.
- **DRAW-29** The board wins (global card §3) and its written copy (msot/sot text) is fixed to the board on disagreement; once a design is locked nothing downstream adds a word, field, table, feature or question the board does not hold (global card §4); every board edit is proposed first as a table (change · page · data change?) and made only on the owner's approve, the board holds state only, with no update note, change note, changelog, version or progress text on any page (the change's history goes to the project's version record at close, owner ruling 2026-10-21), and the repo's text copy of that page and its truth file are refreshed the same session.
- **DRAW-5** Both board links live in the project's repolaneindex row (Board column, reading `state: <link> · workspace: <link>`) and a module's page is linked from its module lane index row.
- **DRAW-2** Figma is worked through the MCP, hand-built in sections: every kind is drawn with `use_figma` (`figma-use` and `figma-use-figjam` loaded first) as shapes, connectors and tables inside its section so it sits where FIG-2 and DRAW-8 place it, copying the board's shape (DRAW-49); a native `generate_diagram` object cannot live in a section, so it serves only as a throwaway sketch outside the board's pages and never as the approved drawing; the owner's in-app edits are re-read through the MCP, and a sketch the MCP cannot read is asked for as a screenshot, never claimed as read (boards approved 2026-10-11, the law aligned 2026-10-15).
- **DRAW-3** After every create or update, screenshot and look (text readable, nothing overlapping, arrows not crossing screens) before sharing the link.
- **DRAW-4** One name, four surfaces (global card §5): design pages carry the design-time domain codes from the lane index, and shipped function, folder and table names appear only in brackets as evidence of where a domain lives today.
- **DRAW-6** The board holds latest only: a replacing drawing deletes the superseded one in the same pass.
- **DRAW-7** A change that alters a flow, boundary, table or screen updates its page in the same change; an approved addition is drawn into the drawing it changes, never parked beside it as an "additions" block, and the owner's own drawings are editable the moment the ruling lands.
- **DRAW-48** A vendor skill's or tool's claim about what the Figma API cannot do is probed on the board before it shapes a drawing (a page is never parked as a section elsewhere on such a claim), and the probe's result is written to `rsot/knowledge/figma-mcp-mechanics.md`.
- **DRAW-50** Every kind is drawn by its seat, dispatched with a brief that names the skill, the laws, the reference pages of that kind and the owner's confirmed intent (LEAD-20: `architect` the index, CDT, ERD, context map, flows and infrastructure · `database-engineer` the data schema · `uxui-designer` the user flows); the main loop proposes, briefs and verifies and never draws a kind itself, a user flow is never drawn before the owner has stated the journey's intent (UX-10), and a flow drawn from a guessed list is deleted, not fixed (owner ruling 2026-10-16).
