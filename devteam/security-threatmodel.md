# Dev team — Threat modelling & the security test plan (SEC §8)

Type: Law (threat-model method for `security.md`) · pulled through rulesindex when running a critical-function review — naming the top 3, enumerating abuse cases, or executing the pre-production pass. Update: one rule = one line; replace the line and delete the superseded one in the same edit. The reasoning and the incident behind each rule: `rsot/knowledge/security-threatmodel-rule-rationale.md`, same rule IDs, open when a rule's judgment is in play.

- **SEC-30** At design time security asks the architect and the operator, per domain, for the top 3 critical functions (ARCH-33) — those whose compromise costs money, trust or control — and only those get bespoke abuse-case analysis, everything else being covered by the standing rules in `security.md` §1–7.
- **SEC-31** For each critical function the abuse cases are enumerated by path (tampered directly via API, valid session with the wrong role, replayed request, forged signature or webhook, value altered client-side after approval, privilege escalated to admin, reached through a compromised dependency or host, read or exported unauthenticated), never by feature, and each lands as one row of the project's security table (SEC-44), built from the complete project and its approved board beside the architect's failure map (ARCH-29), never accumulated during build (owner ruling 2026-10-28).
- **SEC-32** The security table (SEC-44) is approved by the owner and executed once the whole project is complete, before production exposure (QA-18, the gate SEC-12 requires) — every abuse case on it, the deny path of each (SEC-3) and everything the failure map marked as guarded, the security tester building the tests (SEC-40) and its log filling the security rows of QA's table (QA-17) — a critical function whose abuse cases have never run is unproven, and the pass targets only systems Raze owns, never exploit development (owner ruling 2026-10-28).
