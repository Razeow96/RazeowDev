# Drawing law · CDT contract test script (cross domain transmission + its contracts)

Type: Law · the CDT contract test script: how it is drawn, in every repo · pulled through rulesindex when drawing a CDT or a contract test, together with index-and-legend.md. Update: one rule = one line; replace the line, never add beside it; IDs are append-only. Owner ruling 2026-10-23 (after the WC-A / WC-B contract failure of that night): the plain CDT is retired; its crossings stay, and every arrow now carries the full-body contract that the release tester checks live. Renamed 2026-10-25. Owner ruling 2026-10-28: contract tests are stage 2's alone (TEST-31); the build tester writes no seam test.

Answers: which hand-offs cross a module or domain boundary, what the full body of each hand-off is, and what proves it on both ends. Sits on its own page, one per project, named `<n> · CDT contract test script`, one section per group of crossings named `<n>.<k> · CDT contract test script — <name>`; the decision table tree and the end to end test script are pages of their own (owner ruling 2026-10-26). Seats: architect draws it (`/architecture-ddd-draw`); the release tester keeps the contract files it mirrors (REL-4) and writes the contract checks once the project is complete (REL-1). Altitude: field of the body (DRAW-28). How to design what a payload carries: knowledge file `rsot/knowledge/event-payload-design.md`.

- **DRAW-31 CDT contract test script.** Top of the section: the parts (modules, the sheet, the store, every outside service) as boxes in flow order, with one arrow per hand-off that crosses a boundary, at most five per domain, each arrow labelled with the contract's id (the release suite's check id, `C<n>`, when one exists). Below: one contract card per arrow = the full body: a header (hand-off name · version · origin → destination · form of the hand-off: HTTP body, table row, file at an address, sheet cells · the one spine key) over a table with one row per field: `field · type · required · allowed values · example · origin table.column → destination table.column or port`, where the destination is written as itself, never a table invented to fill the column; a key crosses only when the destination writes it or branches on it; a body that equals a contract already drawn is one row pointing at that card, never listed again; the five-data cap (ARCH-37) applies to every body. Under the table, one `expected result` row per direction (payload shape, status, exact count, time; what the receiver mints, derives or looks up itself, so every absent field is explained), then `proved by: contract check <id> (live, release tester)`, and the card's single home: the contract file in `release-tests/contracts/` whose facts it mirrors (REL-4); a card and its contract file that disagree is a defect on the newer one. A field with no designed destination, no expected result or no proof is red, and the red rows are the build list; a crossing with no expected result is not drawn as done. Today's live result (PASS / FAIL and the date) is written on the card from the release suite's run of record, never by hand (owner rulings 2026-10-19, 2026-10-22, 2026-10-23, 2026-10-28).
- **DRAW-41 Everything else is named, not boxed.** A hand-off that is a plain table read inside one module, or a record no other part branches on, is not a crossing and gets no card; the section note lists those reads in one line, so the reader sees that every boundary was classified.
- **DRAW-42 Additive versus breaking change.** Adding a field bumps the contract's version and keeps its name; removing, renaming or retyping a field, or changing an allowed value (a template name, a code word, an accepted cell value) is breaking and mints a new version, and the change lists every consumer it updated (REL-6); the header shows the live version; a header and card that disagree on the version is a defect fixed on sight.
