Type: Law · the decision table tree test script: how it is drawn, in every repo · pulled through rulesindex when drawing a decision table or briefing the build tester's rule tests, together with index-and-legend.md. Update: one rule = one line; replace the line, never add beside it; IDs are append-only. Answers: every rule the system decides by, as a table whose columns are the tests, and how one rule's outcome feeds the next. Sits on its own page, one per project, named `<n> · Decision table tree test script` (owner ruling 2026-10-26). Seats: architect draws it; tester 1 runs one case per column (TEST-38) and reports a column with no passing run as a FAIL line. Altitude: rule (DRAW-28).

- **DRAW-54 Decision table tree.** One table per rule the code branches on (a class decision, a format or template choice, a hold-or-ship decision, a send decision): rows are the conditions, with the outcome as the last row; each column is one case = one test, headed by its test id; a cell holds the condition's value for that case or `—` when it does not matter; the outcome row names the exact word the code writes (class letter, template name, hold note family, provider). Tables are linked like an ERD: an arrow from a table's outcome row to the condition row of the table that reads it, labelled with the field that carries the outcome (`lead_campaigns.lead_class`, `run_settings.proposal_template`), so a reader can walk a lead from the first table to the last. A rule whose words live in a settings sheet or a fixed-rules file names that home in the table header; the table never restates a value the home already holds beyond the cases it tests. A column with no test, or a case the code can reach that no column covers, is red, and the red columns are the build list. A gate (deploy, go-live, approval) is never a table here.
