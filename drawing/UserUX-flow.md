# Drawing law · User UX flow

Type: Law · the user UX flow kind: how one persona's journey is drawn, in every repo · pulled through rulesindex when drawing a user flow, together with index-and-legend.md. Update: one rule = one line; replace the line, never add beside it; IDs are append-only. Renamed from user-flow.md on the owner's ruling 2026-10-16.

Answers: one persona's job, from the moment it starts to the state it ends in. First the **user functionality flow**: what the person does, step by step, with every question and every branch. Then under it the **user experience flow**: the screens those steps happen on, web and phone, wired by the control that leads on. Drawn by the UX/UI designer through `/uxui-userflow-draw` (LEAD-20, DRAW-50) after the owner has stated the journey's intent (UX-10). Reference of record: Content OS board pages 5.1 to 5.5 (approved 2026-10-07). The functionality flow sits at the top of the journey's page and the UX flow is a section under it on the same page (FIG-2, DRAW-1); both copy the Content OS shape (`figma-drawing-recipes.md`); each page has a text copy in the repo's board folder. UX is this kind; UXUI is the look law (`devteam/uxui.md`) and never this file's subject.

- **DRAW-24 User functionality flow.** The page header names the persona, the goal, the fear, the main-path step count, the branches by kind (empty · error · permission) and the claims the product may make to that persona; the main path runs top to bottom as numbered steps in the persona's words, the thing he does ("Open the 09:00 post", "Approve or reject, one tap"), never a menu press, a feature name or a code; every diamond is a question about his world ("Anything waiting?", "Slot still open?", "Facebook accepted it?"), never a system check; every branch ends in a real end-state box coloured by the legend (yellow empty or open decision · red missed, failed or refused · the done state a white rounded box) and a retry branch arrows back to the step it retries; a path longer than its stated count is a finding, not a drawing.
- **DRAW-36 User experience flow.** A section under the functionality flow on the same page (FIG-2): a web lane (desktop 720 × 450) then a phone lane (300 × 640, the primary button in a pinned bottom bar), the same journey in both; one screen per step and per branch, each under a violet tag naming its step and route; every control is its own node (app bar, chip, row, button, input, toggle) and every arrow leaves the control that leads on, lands on the next screen and carries that control's name and condition ("Approve · slot still open"); a decision outside the product is a purple box fanning out to its branch screens; Back, Try again and Cancel are controls like any other and their arrows return to the screen they lead to; every control traces to a column on the data schema pages and shows nothing a column or a ruling does not hold; loose screen pictures, text-block screens, or an arrow that leaves a screen instead of a control are not a user flow and are deleted, not fixed.
- **DRAW-51 The journey comes from the persona, never from a list.** A user flow is drawn only for a job the persona has, stated and confirmed by the owner before the first shape (UX-10: who, in which moment, how often, what he fears); a journey derived from a menu, a feature list or the seat's own candidates is refused; an idea the owner has not ruled is drawn only as a page titled `PROPOSAL, not ruled` with nothing built on it; the seat draws only what the owner has stated.
- **DRAW-52 Text copy per page.** Every user-flow page has a text copy in the repo's source-of-truth board folder (`msot/board/<page>-user-flow-<slug>.md` in Content OS, the equivalent elsewhere): the header line, the steps and connectors in order, and a screen table (screen · step tag · controls drawn · buttons → where they lead), refreshed in the same session as the page (DRAW-29); the board wins over the copy.
